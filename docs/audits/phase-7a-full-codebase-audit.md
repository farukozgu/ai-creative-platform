# Phase 7A — full codebase audit

Date: 2026-10-22. Scope: repository-only, read-only investigation. No application or test code, database, deployment, provider, worker, or billing state was changed. The only repository change is this report. Findings describe repository behavior, **not** verified production behavior. The linked Supabase schema and deployed environment were not queried.

## 1. Executive summary

No confirmed critical authentication bypass, cross-tenant data read, secret leak, or live customer-credit charge was found in the traced entry points. That is not a penetration-test result. The most urgent confirmed issue is an authenticated, immediately reachable image-edit action that can repeatedly initiate paid OpenAI requests without the queued generation path's submission idempotency, quota, or concurrency budget (F-01). A separate forced product reanalysis action also bypasses the normal analysis cache (F-02). The closed video, Model Studio candidate, identity-conditioned generation, and billing gates appear intentionally closed in source and must be preserved.

The automated baseline is green (72 pretest tests, 593 main-script tests, and 52 separately run omitted tests; lint, TypeScript, build, and diff check pass). Green checks do not establish database deployment, RLS behavior, browser appearance, accessibility, provider economics, or production readiness. Fourteen focused suites are not included in `npm test` (F-03). The Model Library currently depends on an undeployed schema and reports a generic route error rather than a purpose-built schema-unavailable state (F-04).

## 3. Security, financial, database, and workflow findings

Severity is based on *current reachable code*, with dormant/deployment-conditional risks labeled separately. “Safe without deployment” means source/test change can be prepared locally; it does not authorize production activation.

### F-01 — High — security/financial abuse — unbounded paid image-edit submissions (confirmed, reachable)

Evidence: `src/lib/generation/image-worker-service.ts:147-177,181-225`; browser action wrapper `src/app/[locale]/dashboard/projects/[projectId]/generation-actions.ts:26-32`; compare queued idempotency `image-worker-service.ts:396,445-475`. The edit checks authenticated project/base ownership and validates the instruction, but every call inserts a fresh processing row and can perform an initial and repair image request. There is no edit submission key, per-user active-job cap, quota, or entitlement/credit decision in this path. Scenario: an authenticated account retries or parallelizes edits of an owned successful image. Impact: provider cost amplification and concurrent request load; no claim of cross-user access or customer charging. Confidence: high from source; production invocation/cost unverified. Remedy: apply a server-side idempotency key and bounded per-user admission/concurrency/cost policy before provider submission; test repeated/concurrent calls and uncertain outcomes. Regression risk: high (edits/retries/partial results); safe without deployment: source/tests can be prepared, but effectiveness requires an appropriate DB constraint or equivalent atomic store and controlled rollout.

### F-02 — High — security/financial abuse — forced product reanalysis bypasses cache (confirmed, reachable)

Evidence: `src/app/[locale]/dashboard/projects/[projectId]/actions.ts:236-243` always calls `analyzeProductAsset({ force: true })`; `src/lib/product-understanding/product-analysis-cache.ts:41` returns `analyze` on force before retry-window handling; `analyze-product-asset.ts:121-166` verifies ownership then reaches the paid analyzer. Scenario: repeat action on the same owned asset, including during transient provider failure. Impact: avoidable OpenAI spend and load; the ownership check prevents an obvious IDOR. Confidence: high. Remedy: rate/concurrency budget forced reanalysis and restrict force to an explicit justified state; retain ordinary cache behavior. Regression risk: medium (manual retry UX); safe without deployment: yes for code/tests, though a durable distributed throttle may need storage rollout.

### F-03 — Medium — test coverage — default test command omits 14 suites (confirmed)

Evidence: explicit `pretest`/`test` file lists at `package.json:6,14`; directory inventory has 76 test files, 14 absent from both lists: `composer-model-selection-foundation`, `cost-accounting`, `credit-source-lifecycle`, `editorial-fashion-classification`, `financial-read-permissions`, `identity-fidelity-foundation`, `model-candidate-engine`, `model-candidate-foundation`, `model-candidate-hardening`, `model-candidate-orchestration`, `model-candidate-review`, `model-library-search`, `model-persistence-foundation`, `model-profile`. Scenario: changes pass CI/local `npm test` while Model Studio or finance tests were never invoked. Impact: misleading regression signal. Confidence: high; separately executed omitted suites passed 52/52. Remedy: use a discovered, deterministic test glob or maintain an audited manifest while preserving pretest ordering. Regression risk: low/medium (test environment or sequencing); safe without deployment: yes.

### F-04 — Medium — workflow/UX — Model Library treats pending schema as generic route failure (confirmed code path, schema pending)

Evidence: `src/lib/models/model-profiles.ts:8` throws on query failure; `src/app/[locale]/dashboard/models/page.tsx:10` awaits it without fallback; `src/app/[locale]/dashboard/models/error.tsx:1-3` renders generic `RouteErrorState`. Detail page has an explicit schema-unavailable branch at `src/app/[locale]/dashboard/models/[modelId]/page.tsx:11`. Scenario: a user opens Model Library before migrations are verified/applied. Impact: generic error instead of the intended unavailable explanation, potentially confusing a known deferred feature with an outage. Confidence: high for source, actual DB schema unverified. Remedy: use the established localized unavailable state and distinguish missing schema from transient errors without masking real failures. Regression risk: low/medium; safe without deployment: yes.

### F-05 — Medium — localization/data modeling — localized labels persisted as model trait values (confirmed, dormant data path)

Evidence: `src/features/models/model-create.tsx:31` uses translated option *text* as `<option value>`; `src/lib/models/model-profiles.ts:10-11` persists those values and `model-create.tsx:20,31` rehydrates them; TR/EN values differ at `src/messages/tr.json:691` and `en.json:693`. Scenario: create a draft in Turkish, switch to English; several select `value`s have no matching English option, or future candidate prompts mix languages. Impact: confusing edit state and noncanonical identity traits. Confidence: high static; no persisted user records assumed. Remedy: stable locale-neutral option IDs with translated display labels and an explicit migration/compatibility plan if records ever exist. Regression risk: medium; safe without deployment: only before any real records, otherwise staged data migration.

### F-06 — Medium — data lifecycle — project deletion leaves storage lifecycle unspecified (confirmed source gap)

Evidence: `src/app/[locale]/dashboard/actions.ts:83-115` deletes only `public.projects`; storage uploads live in `product-assets`, `generated-assets`, and potentially video buckets (for example `src/app/[locale]/dashboard/projects/[projectId]/actions.ts:76-173`, `src/lib/generation/image-worker-service.ts:1688`). Database FK cascades remove metadata, not Supabase Storage objects; no storage removal is called by the delete action. Scenario: delete a project containing uploaded/generated media. Impact: orphaned private objects and storage cost; exact deployed cascade/storage state unverified. Confidence: medium-high. Remedy: design an idempotent, owner-scoped, failure-recoverable media cleanup, with careful handling of in-flight jobs and shared references; audit existing objects before deletion. Regression risk: high (data deletion), safe without deployment: design/tests yes, production cleanup no.

### F-07 — Medium — database integrity — latest Model Studio migration still allows owner-side approved-status downgrade (deployment-conditional)

Evidence: `database/migrations/20261030000000_create_model_identity_foundation.sql:78,83` grants owner update and permits resulting draft/archived statuses; latest `20261031030000_harden_model_candidate_integrity.sql:5-9` blocks unauthorized *approval* but does not prohibit `approved → draft/archived`. The repository action limits updates to drafts (`src/lib/models/model-profiles.ts:11-12`), but a client can invoke Supabase with its own credentials if policies are deployed. Scenario: an owner (or buggy client) changes an approved profile to draft while its version/pointer remains; the future approval transaction sees an existing identity version and rejects another candidate. Impact: self-inflicted identity-state inconsistency/availability; no cross-tenant read established. Confidence: medium static; migrations not deployed/verified. Remedy: specify allowed transition graph and enforce old/new status plus pointer invariants in one trusted DB boundary; test direct authenticated writes. Regression risk: high; safe without deployment: migration revision/verification plan only, no application of migrations in this phase.

### F-08 — Medium — workflow/reliability — queue accepts image work while executor is disabled (confirmed design tradeoff)

Evidence: `src/lib/generation/image-worker-service.ts:324-485` accepts and inserts queued work without checking `IMAGE_GENERATION_WORKER_ENABLED`; `src/lib/generation/image-scheduler.ts:19-22` and `src/lib/generation/image-worker-handler.ts:11-15` gate only execution. Scenario: Composer is used in an environment where the scheduled worker remains intentionally off. Impact: jobs can remain queued indefinitely, while user-facing generation progress implies work is advancing. This separation is deliberate for durable admission and is **not** a reason to activate the worker. Confidence: high static. Remedy: clarify UI/status messaging and operational readiness policy for disabled executor, without collapsing durable architecture. Regression risk: medium; safe without deployment: yes for message/status changes.

### F-09 — Medium — performance — unbounded project/model reads and per-item preview signing (confirmed scalability risk)

Evidence: `src/lib/projects/get-projects.ts:54-78,103-121` signs one preview per project and allows `getProjects` without a limit; `getProjectsPage` uses page size 16 at `src/app/[locale]/dashboard/projects/page.tsx:40`. `src/lib/models/model-profiles.ts:8` lists all profiles; `src/lib/models/candidate-review.ts:13-29` loads all candidates and signs each preview. Scenario: account accumulates a large library; server read time and Supabase Storage signing requests grow with records. Impact: latency, request pressure, and memory growth. Confidence: high static; no production volume measurements. Remedy: retain project pagination; add bounded model/candidate pagination and batch/limited preview signing, measure before optimizing. Regression risk: medium; safe without deployment: yes if schema/query contracts permit.

### F-10 — Low — localization/UX — locale-dependent search/date behavior is not tied to route locale (confirmed)

Evidence: `src/features/models/model-library.tsx:17,37` uses `toLocaleLowerCase()` and `Intl.DateTimeFormat(undefined, ...)`, relying on browser locale, not the active `tr`/`en` route. Scenario: Turkish dotted/dotless-I matching or date formatting differs from the visible language. Impact: inconsistent search and date presentation. Confidence: high static, actual browser behavior untested. Remedy: pass the active locale and test Turkish casing/date cases. Regression risk: low; safe without deployment: yes.

### F-11 — Low — localization — default project title is hardcoded Turkish in both locale routes (confirmed)

Evidence: `src/app/[locale]/dashboard/actions.ts:27` and `src/app/[locale]/dashboard/projects/[projectId]/actions.ts:55` use `İsimsiz Proje`; AGENTS.md requires TR/EN user-visible copy. Scenario: an English-route action submits an empty title. Impact: mixed-language project name. Confidence: high. Remedy: resolve localized default at the action boundary or use a neutral stored title plus translated display fallback. Regression risk: low/medium (persisted title semantics); safe without deployment: yes.

### F-12 — Low — documentation — README describes obsolete architecture (confirmed documentation debt)

Evidence: `README.md:3-25` says only navbar/footer exist, lists Outfit and `src/config`, and says image generation is synchronous with durable background work deferred. Actual code uses Geist/Manrope, has no `src/config`, and implements queued image jobs and worker lease contracts (`src/lib/generation/image-scheduler.ts`, `database/migrations/20261027*`). Scenario: an operator follows README to plan deployment or debugging. Impact: wrong expectations and unsafe setup decisions. Confidence: high. Remedy: update documentation after architecture facts and deployment state are confirmed. Regression risk: low; safe without deployment: yes.

### F-13 — Low — input validation — reference image registration checks metadata but not decode (confirmed validation asymmetry)

Evidence: `src/app/[locale]/dashboard/projects/[projectId]/actions.ts:270-291` checks extension, MIME, and 20 MiB size then inserts reference metadata; product registration at `actions.ts:111-154` additionally decodes image geometry. Scenario: malformed bytes carrying an accepted MIME type become a reference record; downstream analysis/generation may fail or incur validation work. Impact: user-visible failure and possible wasted provider preparation; no demonstrated execution or cross-user risk. Confidence: high static. Remedy: share bounded image decode/geometry validation before registration, respecting existing product rules. Regression risk: low/medium; safe without deployment: yes.

## 4. Security controls and unresolved attack-surface checks

- Authenticated actions generally call `getAuthenticatedUserId()` (`src/lib/auth/require-user.ts:3-15`), and sampled project/model/video queries constrain owner IDs. Private model references additionally require owner-scoped DB rows and return `Cache-Control: private, no-store` (`src/app/api/model-reference/[referenceId]/route.ts:7-20`). This is source-level evidence, not live RLS proof.
- Worker endpoints use server-held Bearer secrets, a timing-safe comparison (`src/lib/video-generation/scheduler-auth.ts:1-9`), and independent execution gates. Video submission has entitlement, capability approval, and final billing-unavailable checks (`src/app/[locale]/dashboard/video/generation-actions.ts:13-25`). Do not remove these.
- SQL policies enable RLS on core owner tables; Model Studio storage is private and lacks authenticated upload permission (`database/migrations/20261030000000_create_model_identity_foundation.sql:72-88`). Latest candidate migration adds owner-matching triggers (`20261031030000_harden_model_candidate_integrity.sql:11-21`). Actual installed policy versions, grants, triggers, and transaction behavior are unknown.
- Video output download checks HTTPS and an allowlist, rejects redirects, uses a 60-second timeout and streamed byte cap (`src/lib/video-generation/output.ts:5-42`). Provider-supplied URLs remain a future SSRF-sensitive boundary; preserve/strengthen allowlisting during activation. No provider URL was fetched here.
- Thematic searches found no application `dangerouslySetInnerHTML` use except a static theme-init script (`src/components/theme/theme-init-script.tsx:6`). This does not replace a dynamic XSS review. Next server-action origin/CSRF controls were not exercise-tested. Dependency advisories were not queried; no vulnerability assertion is made.
- Secret values were not read or printed. `.env.example` contains names and intentionally false worker/video defaults. `proxy.ts:28-33` logs raw session-refresh errors; inspect log redaction before deployment, but no actual secret exposure was demonstrated.

## 7. Architecture and maintainability

`src/lib/generation/image-worker-service.ts` is about 2,000 lines and handles both synchronous image edits and durable queued execution; `src/components/dashboard/creative-composer.tsx` is about 960 lines. Their size creates change-coupling, but splitting them without behavior-specific tests would be a speculative rewrite. F-01 is a concrete seam for extracting a shared provider-admission contract; F-03 is a concrete test-manifest problem. Source uses a number of database-row `as unknown as` casts (for example `src/lib/projects/get-projects.ts:121,148` and `src/lib/generation/image-worker-service.ts:549`); generated Supabase types would reduce drift, but no runtime type failure was confirmed. The dashboard's user-scoped repository pattern is generally consistent. Error handling often returns generic failures, which is appropriate for private internals but needs explicit user-facing deferred-feature states (F-04/F-08).

## 16. Limitations and assumptions

This is static repository analysis plus local test/build execution, not a live security assessment. The production-equivalent Supabase project, deployed migration ledger, current environment flags, storage contents, payment/provider accounts, advisory services, and Vercel state were not accessed. No real user models, images or credits were fabricated or mutated. Security conclusions assume repository code is what would be deployed; remote policies/functions may differ. SQL transactional behavior and RLS were not run against a database. Browser automation was not available as part of this audit workflow, so responsive, theme, focus and screenshot claims remain unverified. There were no production console or telemetry logs. In particular, the unresolved Model Studio migration verification blocker must be cleared independently before any Model Studio activation or migration change.
